# 声境项目框架、四人分工与赛程路线图

团队讨论稿 · 2026 年 11 月 18 日 · 开发基线 0.4.0

## 1. 最终用户能做什么

面向听障人士和听力下降的老年人，主攻宿舍与家庭里的三个声音事件：敲门、门铃、闹钟。作品对应赛题 2「AI 融入日常——面向移动终端的系统级智能体验创新」。

一个完整的使用情节是：用户选好想关注的声音，把手机放在桌上。来客敲门时，手机在本地识别，按当前场景决定是否提醒，手表振动并显示“可能有人敲门”。用户可以在腕上确认，也可以稍后在手机回看或标记误报。学习时同一个人连续敲门，应尽量减少打扰。最终用户知道设备在听什么、为什么提醒、怎样暂停，也能决定是否采纳个人偏好建议。

截至本稿，0.3.0 已验证一次真实敲门触发手机提醒并同步手表。0.4.0 已合并并通过自动检查，增加本机历史、偏好和手动选择的居家／学习策略，待真机集中验收。端侧模型已有公开集基线；门铃独立正样本、噪声下可靠性、长期锁屏和目标用户体验仍需补证。下文的验收目标和个性化建议属于后续规划。

## 2. 系统怎样协作

| 环节 | 负责人及输入 | 输出与交接 |
|---|---|---|
| 采集和设备状态 | A 管理手机麦克风、权限、启动和停止 | 为 B 提供可用的音频窗口、采集时间与诊断。产品运行时原始声音只在内存处理。 |
| 声音感知 | B 接音频窗口，在手机本地推理 | 给 C 每类声音的模型分数、事件时间和类别；向 A 暴露采集或推理故障。分数用于比较和判定，不作为识别正确的概率。 |
| 提醒决策 | C 接候选分数、用户关注类别、所选场景、暂停状态和近期事件 | 给 A 是否提醒、理由及提醒方式；给 D 稳定的原因标签，供回放比较。B 提供阈值实验，C 将选定的策略用于实际决策。 |
| 手机、手表与反馈 | A 执行系统通知，承接通知同步、记录和操作回传 | 用同一事件编号关联识别、提醒请求与用户反馈。手机可证明已请求系统通知；腕上是否实际到达由佩戴者观察验证。 |
| 数据与评测 | D 组织独立样本、持续背景、测试流程与目标用户任务 | 给 B 错误类别和开发样本，给 C 过度打扰与漏提醒案例，给 A 故障复现条件，给全队独立验收结果。 |

## 3. 每个人负责到底的板块

### A · 手机、手表与整机集成

- 建议由持有 Find X8 Pro 和 Watch X2 的队员担任。统一负责设备接入、Android 生命周期、通知和手表同步、页面、设置保存、记录清空、固定签名包及真机联调。A 决定每一轮使用哪个包与设备配置。
- 最终交付可覆盖安装的 APK、日常使用界面、设备设置与故障恢复说明、可重复的现场演示流程。把监听、暂停、确认和停止做成用户能独立完成的操作，把开发诊断放在次级入口。
- 验收时请一名未参与开发的人从授权开始完成一次提醒和反馈。另测锁屏、断连后重连、通知关闭和停止后麦克风释放，记录实际结果。断连期间界面应准确表达已知状态，腕上送达以实测为准。

### B · 音频识别与端侧模型

- 负责声音窗口、模型输入、三类输出、复杂环境识别与端侧推理耗时。先补齐门铃，分析脚步、木门吱呀、敲桌等混淆，再决定采用现有模型、阈值校准或轻量分类器。
- 最终交付可由 A 集成的离线识别模块、模型与参数版本、基线和候选方案比较、各类典型失败案例。B 必须能解释改了什么、改善了哪类声音、代价是什么。
- 验收用 D 事先保留的房间或声源，逐类给出命中数／实际事件数、误报和端侧推理耗时。独立测试结果若用于下一轮调参，就为新版本另留验收数据。

### C · 场景决策、提醒方式与个人偏好

- 负责“这个声音此刻值不值得提醒”。维护关注类别、场景、连续事件合并、冷却、提醒原因及振动策略；A 实现手机和手表上的显示与执行。当前居家敲门最短间隔 15 秒，学习为 60 秒，门铃与闹钟各自保持 15 秒。
- 最终交付能回放和解释的策略模块。先实现相同声音在两个场景下的不同处理；进阶做一条可验证的个性化能力，例如用户多次明确表示某场景不想被打扰，系统提出调整提醒频率的建议，确认后生效，设有恢复入口。将“声音认错”和“认对了但我不想被提醒”分别收集。
- 验收时给两种场景输入同一段带时间戳的事件序列，显示首次提醒、连续敲击合并、下一次提醒被允许的时刻及原因。与 D 比较重复打扰下降了多少、有没有同时压掉用户需要的新事件。

### D · 数据、独立评测与用户验证

- 负责数据来源和许可、样本分组、标注、回放工具、端到端测试设计和用户试用。按声源、房间或采集场次拆分开发与验收数据；一段音频的多个窗口不能算多个独立事件。原始采集材料和参与者信息留在受控位置，仓库仅收脱敏结果。
- 最终交付可复跑的评测脚本、版本对比表、真实环境失败案例、用户任务结果和比赛测试报告。朋友可先做流程走查；听障或听力下降使用者亲自参与的结果单独统计。
- 验收看四类证据：各声音事件召回、每小时误报、从实际声音到观察到提醒的延迟、用户能否觉察并理解提醒。每项写清样本数、时长、设备、环境和测量方法。一次推理耗时和整条提醒延迟分别报告。

**协作约定**：A、D 在同一场集中真机测试里协作。A 操作版本、设备并定位问题，D 预先写好场景、记录预期与实测并复核结果。这样设备调试只有一个负责人，同时保留独立评测。四个人都能独立用固定输入开展日常工作，每次阶段集成统一出包。每项改动由负责人提交普通 PR，仓库负责人审核合并。AI 可协助编程和整理，模块负责人承担代码解释、复现和答辩。

按附件八，初赛创新性占 40 分，应用价值、软件技术、软件工程质量分别为 20、25、15 分；后续阶段依次为 20、30、30、20 分。初赛优先讲清用户遇到的具体困难、同类功能对照与方案可行性；后续用目标用户试用、独立数据和实机性能支持主张。各阶段材料提交前统一检查匿名评审要求。

## 5. 现场演示与取舍

建议准备三分钟主线：A 在手机开启监听，一位队员真实敲门，佩戴者在手表查看并确认，A 打开历史记录。C 用同样的后续事件展示学习与居家的不同处理，显式标明回放环节。B 展示三类声音的端侧结果及一个典型混淆，D 展示真实试用和独立评测表，并说明一次失败如何推动改进。现场设备、真实录制视频和模拟演示各自标明来源。

三类声音、跨设备反馈、场景差异和独立评测优先完成。姓名呼叫、声源方向、外接阵列或独立手表 App 留作经验证有需求后的扩展。一个能由用户确认、撤销且测得效果的偏好建议，优先级高于同时再加多个声音类别。
